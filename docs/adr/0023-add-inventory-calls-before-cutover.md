# ADR-0023: 흐름별로 inventory 호출을 먼저 추가하고 읽기·쓰기 컷오버는 마지막에 한 번에 한다

## 상태
Accepted (ADR-0018 결정 5의 흐름별 전환 방식을 대체)

## 배경 (Context)
[ADR-0018](0018-location-stock-ledger.md) 결정 5는 F-032~F-036에서 흐름마다 "미러링 → inventory 연동 + 장부 직접 갱신"으로 바꾸고
F-037에서 레거시를 제거하기로 했다. 구현을 앞두고 보니 이 방식은 중간 상태가 깨진다.

- 기존 `Inventory`·`Lot`·`Allocation` 테이블은 입고뿐 아니라 출고 FIFO 피킹, 폐기 대상 조회, 실사 스냅샷, 반품 재입고, 재고 조회 API가 모두
  읽는다. 입고가 먼저 `Inventory` 쓰기를 멈추면 아직 전환하지 않은 흐름이 틀린 수량을 읽는다.
- 입고 하나를 전환하려면 그 수량을 읽는 모든 흐름의 읽기 경로도 같이 바꿔야 해서 흐름별 PR이 사실상 빅뱅이 된다.

고려한 대안:
- **ADR-0018 그대로 흐름별 전환**: 위 이유로 각 PR이 단독으로 동작한다는 원칙을 지키기 어렵다. 기각.
- **호출 추가와 컷오버를 분리(채택)**: 흐름마다 기존 쓰기·미러링은 두고 inventory 호출 기록만 더한다. 마지막에 읽기·쓰기를 장부로 옮기고 레거시를 지운다.

## 결정 (Decision)

### 1. F-032~F-036: 기존 쓰기와 미러링은 유지하고 호출 기록만 추가한다
- 입고·반품·폐기의 확정 트랜잭션 안에서 `RecordInventoryCallUseCase`로 호출을 아웃박스에 기록한다. 기존 `Inventory` 갱신과 `LocationStockMirror`
  미러링은 그대로 둔다.
- 따라서 이 기간에는 같은 수량이 기존 `Inventory`, 장부, inventory 서비스에 있다. 장부는 미러링으로 갱신되므로 `stock-quantities`(F-029)는
  inventory 대사에 쓸 수 있는 값을 계속 준다.
- 실사 조정(F-036)은 예외로 아웃박스를 쓰지 않고 마감 시 inventory를 동기로 호출한다(ADR-0017 결정 5: inventory 판단을 기다리는 작업). 가용 수량 초과(409)·승인
  누락(400) 같은 업무 거부가 많아, 아웃박스로 보내면 `DEAD`로 창고 큐를 멈추고 현장은 마감이 끝난 뒤에야 알게 된다. 로컬 반영을 마친 뒤 마지막에 호출하고
  거부·불가면 예외로 로컬 반영도 되돌리며, 멱등 키(`wms-stock-audit-{실사 ID}`)로 다시 마감해도 중복 반영되지 않는다. 같은 창고에 미전송(`PENDING`)·격리(`DEAD`)
  호출이 있으면 순서가 꼬이므로 마감을 거부한다. 항목은 Location이 아니라 상품×Lot×품질로 합산해 보내고(합이 0이면 제외), 승인 필요 판단은 Location 항목과 합산
  기준 중 엄격한 쪽을 따른다.
- 피킹 불가 Lot 재할당(F-038)도 inventory 판단(대체 Lot 선택)이 필요해 동기로 호출한다. 부족 보고는 inventory에서 신규 할당 보류가 먼저 확정되므로 거부돼도 보류는 남고, 멱등 키 회차(`wms-reallocation-{출고 ID}-{회차}`)는 로컬 반영 뒤에만 올려 같은 회차로 재시도할 수 있다.
- 폐기(F-033)는 확정 호출만 기록한다. `LOT_EXPIRED` 수신(Lot 단위 수량을 Location별로 배분해 폐기 신청 생성)과 부분 폐기 허용은 장부 기준 전환이 필요해
  F-037에서 정한다. 그 전까지 폐기 신청은 지금처럼 등록 API로 만들고 수량은 재고 행 전량이다.
- 출고(F-035)는 진입점이 `RESERVATION_CONFIRMED` 이벤트로 뒤집히므로 기존 경로와의 병행 방식을 그 작업에서 따로 정한다.

### 2. F-037: 컷오버
- 읽기·쓰기를 장부 기준으로 옮기고, `inventory`·`lot`·`allocation`·`inventory_history`와 미러링 코드를 제거한다.
- Location `usedCapacity` 갱신은 이때 장부가 소유한다(ADR-0018 결정 2).

### 3. 호출 규칙
- 호출 단위는 inventory의 요청 단위와 맞춘다. 입고는 수령 라인(`InboundReceipt`) 하나가 요청 하나이고, `Idempotency-Key`는 `wms-inbound-receipt-{수령 라인 ID}`다.
  같은 수령 라인을 여러 Location에 나눠 적재해도 호출은 한 건이다(inventory는 Location을 모른다).
- 호출 기록은 `Inventory` 갱신과 같은 `@Transactional` 안에서 한다. 같은 확정이 롤백되면 호출도 남지 않는다.
- 요청 본문과 경로는 inventory API 계약(inventory ADR-0019)을 따른다. 본문은 기록 시점에 만들어 아웃박스에 저장한다.

### 4. 검증
- 흐름마다 호출을 추가한 뒤 두 서비스를 띄워 확정 1건 → inventory 수량 반영 → 대사에서 보정안 0건을 확인한다.
- 이중 반영이 맞으려면 두 서비스의 시작 상태가 같아야 한다. 개발 단계 전제(데이터 이관 없음)에서 양쪽을 reset한 뒤 시작한다.

## 결과 (Consequences)
- 얻는 것: 모든 PR이 동작하는 상태로 머지된다. 흐름마다 실제 연동을 확인할 수 있고 컷오버 위험이 마지막 한 번으로 모인다.
- 감수하는 것: 임시 이중 반영 기간이 F-037까지 길어지고 미러링 코드가 그동안 남는다. 호출이 `DEAD`가 되면 그 창고의 이후 호출이 멈추는데,
  이 기간에는 기존 쓰기가 이미 성공해 있어 WMS 작업은 계속되지만 inventory와 어긋나 대사에서만 드러난다.
- 폐기 확정 호출은 두 서비스의 유통기한 스캔 시차로 `DEAD`가 될 수 있다(WMS 스캔이 먼저 폐기 예정으로 옮겼지만 inventory는 아직 정상 행이라 404/400). 폐기는 승인 → 이동 → 확정을 사람이 진행해
  시차가 대개 하루 안이고, 이 경우 운영자가 재전송한다. 호출 실패 분류(ADR-0019)는 바꾸지 않는다. WMS 스캔은 F-037에서 사라진다.
- 기존 `Inventory`의 로트 규칙(WMS가 Lot을 직접 만든다)과 inventory의 규칙(입고에서만 생성, 유통기한 불일치는 409)이 다르면 호출이 `DEAD`가 될 수 있다.
  F-037에서 WMS의 로트 로직이 사라지면서 해소된다.
